🔐 Garnet Middleware

How middleware.py bridges the WebUI, Privacy Proxy, and LLM — making Garnet's pseudonymization invisible to the user.

What is middleware.py?

backend/open_webui/utils/middleware.py is the biggest file in the project (~4700 lines). It's the heart of Open WebUI's request pipeline — every chat message flows through it.

Garnet adds about 20 lines of custom code into this file to capture privacy metadata (pseudonymized prompt, entity breakdown) from the Privacy Proxy's SSE stream and forward it to the frontend.

Think of middleware.py as the traffic controller: it receives your message from the browser, sends it to the LLM, and streams the response back. Garnet hooks into this flow to grab extra data the Privacy Proxy injects.

How Model Selection Reaches the Proxy

Before diving into the stream, it helps to understand how the model you pick in the UI determines where the request goes — and why the Privacy Proxy sits in the middle.

1
User selects "gpt-4o" in the model dropdown
↓
2
Chat.svelte → POST /api/chat/completions to WebUI backend
↓
3
middleware.py runs auth + filters, prepares body, routes to openai.py router (because model is OpenAI)
↓
4
openai.py reads OPENAI_API_BASE_URL env var — but this points to the Privacy Proxy, not api.openai.com!
↓
5
Privacy Proxy receives the request:
• reads x-openai-base-url header → knows the real destination (api.openai.com)
• reads Authorization header → has the real API key
• pseudonymizes the message body
↓
6
Proxy forwards pseudonymized text to real OpenAI with original credentials
↓
7
Response streams back: Proxy → openai.py → middleware.py, with extra metadata chunks injected
↓
8
middleware.py captures pseudonymized_prompt + garnet_breakdown from the stream
↓
9
Final done event sent to browser — UI shows (i) tooltip + entity bars
Key insight: The model selection doesn't put anything in x-headers. WebUI just overrides the base URL via env var to always hit the Privacy Proxy. The proxy then uses x-openai-base-url (forwarded by openai.py) to know where to actually send the pseudonymized request. middleware.py only handles the response stream — it captures Garnet metadata, it doesn't build or route the request.

The Full Garnet Flow

1
User types "Max Mustermann at Enclaive" and clicks Send
↓
2
Chat.svelte sends message to /api/chat/completions
↓
3
middleware.py intercepts the request — runs filter functions, prepares the body
↓
4
Request goes to Privacy Proxy (FastAPI :8080) instead of directly to Ollama/OpenAI
↓
5
Privacy Proxy pseudonymizes → sends "PERSON_cc75010d at ORGANIZATION_bd3a68a5" to LLM
↓
6
Privacy Proxy returns SSE stream with extra metadata chunks: pseudonymized_prompt, garnet_breakdown
↓
7
middleware.py reads the stream — captures those metadata chunks, stores them in variables
↓
8
At end of stream, middleware appends metadata to the final SSE done event
↓
9
Chat.svelte receives done event → shows (i) tooltip with pseudonymized prompt + entity bars

The 4 Garnet Variables

These 4 variables are initialized at the start of each stream and filled as the SSE chunks arrive:

# Initialized per-request (line ~3485) pseudonymized_prompt = None # "PERSON_cc75010d at ORGANIZATION_bd3a68a5" file_entity_count = 0 # How many PII entities found in uploaded file garnet_breakdown = {} # {"PERSON": 2, "ORGANIZATION": 1, ...} query_variants = [] # Query expansion variants (HyDE)

How the SSE Stream is Read

Inside stream_body_handler(), middleware reads every SSE line from the Privacy Proxy:

# For each line in the streaming response (line ~3556) async for line in response.body_iterator: # Parse the JSON data from "data: {...}" data = json.loads(data) # 🔑 Garnet's hook — capture privacy metadata if 'pseudonymized_prompt' in data: pseudonymized_prompt = data['pseudonymized_prompt'] if 'file_entity_count' in data: file_entity_count = data['file_entity_count'] if 'garnet_breakdown' in data: garnet_breakdown = data['garnet_breakdown'] if 'query_variants' in data: query_variants = data['query_variants'] # ... then forwards the normal LLM tokens to the browser

How Metadata Gets Back to the Browser

At the END of the stream, middleware appends the captured metadata to the final done event:

# Appended to final SSE event (line ~4648) done_data = { "done": True, "content": full_response, # Garnet additions ↓ **({'pseudonymized_prompt': pseudonymized_prompt} if pseudonymized_prompt else {}), **({'garnet_breakdown': garnet_breakdown} if garnet_breakdown else {}), }

What the Privacy Proxy Injects

The Privacy Proxy (backend/privacy_proxy/app/main.py) sends normal LLM tokens PLUS extra metadata chunks:

# Normal LLM token (passes through to browser unchanged) data: {"choices": [{"delta": {"content": "Hello "}}]} # Garnet metadata chunk (captured by middleware, NOT shown to user directly) data: {"pseudonymized_prompt": "PERSON_cc75010d works at ORGANIZATION_bd3a68a5"} data: {"garnet_breakdown": {"PERSON": 1, "ORGANIZATION": 1}} data: {"file_entity_count": 3} # Stream end data: [DONE]

What the Frontend Does With It

ℹ️ (i) Button Tooltip

Shows pseudonymized_prompt — the masked version of what was sent to the LLM. Lets users see exactly what the AI saw.

📊 Entity Breakdown Bars

Shows garnet_breakdown — a count per entity type (PERSON, ORG, LOCATION) shown as bars in the vault card.

📎 File Entity Counter

Shows file_entity_count — how many PII entities were found in an uploaded file before chunking.

🔍 Query Variants

Shows query_variants — expanded query versions for RAG (HyDE), shown in the (i) tooltip.

Why middleware.py is a Conflicted File

Both Garnet AND upstream open-webui modified this file heavily:

Garnet changed Upstream changed
Added 4 Garnet variables + capture logic in SSE loop Renamed CHAT_RESPONSE_MAX_TOOL_CALL_RETRIES → CHAT_RESPONSE_MAX_TOOL_CALL_ITERATIONS
Appends pseudonymized_prompt + garnet_breakdown to done event Added new streaming features, tool call handling, OTEL tracing
Wires file_entity_count through the pipeline Added process_tool_result function + new imports

Since we kept our version ("Accept Current"), the file has Garnet's logic but is missing some variable names upstream renamed — like CHAT_RESPONSE_MAX_TOOL_CALL_RETRIES.

The Current Fix Needed

Problem: Our middleware.py imports CHAT_RESPONSE_MAX_TOOL_CALL_RETRIES from env.py, but upstream's env.py (which we just replaced with) renamed it to CHAT_RESPONSE_MAX_TOOL_CALL_ITERATIONS.

Fix: Add a one-line alias in env.py:
CHAT_RESPONSE_MAX_TOOL_CALL_RETRIES = CHAT_RESPONSE_MAX_TOOL_CALL_ITERATIONS
