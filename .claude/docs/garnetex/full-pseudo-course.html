1. What "full pseudonymization" means

A naive privacy filter cleans only the newest user message before sending to the LLM. That leaks in every conversation past turn 2, because the LLM sees the full history — and older turns still contain the raw PII.

Full pseudonymization means every message in the payload — user turns, assistant replies, retrieved documents, system prompts — is checked and rewritten before leaving the confidential VM. Same PII value always becomes the same anonymous token, so the LLM has a coherent conversation while never seeing the real names.

Concretely: if turn 1 mentioned "Max Mustermann" and turn 5 asks "what was that person's email?", the LLM at turn 5 sees PERSON_dddfab9b in the history — the same token as turn 1. It answers the question from context, and the proxy restores "Max Mustermann" only for the user's screen.

3. The core insight — deterministic hashing

This is the single line that makes everything else work:

def generate_token(entity_type, value):
    h = hashlib.sha256(value.encode()).hexdigest()[:8]
    return f"{entity_type}_{h}"

It only takes the entity type and the value. No timestamp, no session ID, no random salt. That means:

  • Same value → same token, always. "Max Mustermann" always becomes PERSON_dddfab9b, whether it's turn 1, turn 50, chat A, or chat B.
  • No Redis lookup is needed to generate a token — it's a pure function.
  • Two different pods can pseudonymize independently and land on the same tokens.
This is a design choice. Tokens are portable — collision-free is not the design goal, privacy is. The mapping in Redis lets you go backwards (token → original) only for a session that has permission to restore. If a token accidentally ended up in the wrong session, that session couldn't reverse it — no reverse lookup entry.

Why tokens stay stable across turns: two mechanisms, working together —
  1. Deterministic hashing — every fresh Presidio detection produces the same token as before.
  2. Fallback re-scan (pseudonymizer.py:222-227) — even if Presidio's NER misses "Max" on a later turn, the proxy iterates the session mapping and applies each known original → token substitution via regex, longest-first. So no drift.

5. Scenario 2 — two different chats

Chat A session = 189798b8 — user Alice writes "I'm Max Mustermann."

Chat B session = 74963c5b — user Bob independently writes "I'm Max Mustermann."

What happens?

Chat A (Alice)Chat B (Bob)
Presidio detects PERSON = "Max Mustermann" PERSON = "Max Mustermann"
Token generated PERSON_dddfab9b PERSON_dddfab9b ← same!
Redis key garnet:mapping:189798b8 garnet:mapping:74963c5b
Redis value { PERSON_dddfab9b: "Max Mustermann" } { PERSON_dddfab9b: "Max Mustermann" }
LLM sees "I'm PERSON_dddfab9b." "I'm PERSON_dddfab9b."
Response depseudo Uses Alice's session mapping → restores "Max Mustermann" for Alice Uses Bob's session mapping → restores "Max Mustermann" for Bob
Tokens are the same, but the reverse-lookup tables are separate. Bob's chat cannot restore a token that Alice's session generated — even though the token string is identical — because depseudonymization uses the caller's session ID as the Redis key. Alice writing "Max" doesn't leak anything about Bob, and vice versa.
What if we wanted DIFFERENT tokens per session too? The change would be one line — add session_id as a hash input: 
def generate_token(entity_type, value, session_id):
    h = hashlib.sha256(f"{session_id}:{value}".encode()).hexdigest()[:8]
    return f"{entity_type}_{h}"
Trade-off: you'd lose easy debuggability (the same name would look different in each chat's logs) but gain perfect visual isolation. Today Garnet chose portability + readability of debug logs.

6. What's actually inside Redis

After the scenario above, if you did redis-cli KEYS 'garnet:*' inside the confidential VM, you'd see:

$> redis-cli KEYS 'garnet:mapping:*'
1) "garnet:mapping:189798b8"
2) "garnet:mapping:74963c5b"

$> redis-cli GET 'garnet:mapping:189798b8'
"{\"PERSON_dddfab9b\":\"Max Mustermann\",
   \"ORGANIZATION_bd3a68a5\":\"Enclaive\",
   \"EMAIL_ADDRESS_2162ce1b\":\"max.mustermann@enclaive.io\"}"

$> redis-cli TTL 'garnet:mapping:189798b8'
(integer) 3542   # seconds remaining, resets to 3600 on each write
Sensitive: the plaintext originals live inside Redis. That's why Redis runs inside the Enclaive confidential VM with attestation — nobody outside the cVM can read it, and even the cloud provider can't inspect memory.

7. What happens when things go wrong

FailureEffect
Redis is unreachable Fall back to in-memory only (per pod). Restart = mapping lost = old messages can't be depseudo'd. New messages work.
Session TTL (1h) expires mid-conversation Redis key gone. Next turn: Presidio re-detects, deterministic hash → same tokens reconstructed. Depseudo still works because the new tokens equal the old ones.
Presidio misses a name on turn 5 that it caught on turn 1 Fallback re-scan (pseudonymizer.py:222) applies the session mapping via regex — the miss is caught and replaced.
LLM invents a "PERSON_xyz" that isn't in the mapping Depseudo leaves it as-is (no reverse entry). User sees the raw token — a signal that the LLM hallucinated something.
Very long conversation (100+ turns) Every request scans full history — cost grows linearly. Observed ~4-5s pseudo overhead at ~5 turns. Optimization scheduled: skip already-tokenized messages via a flag.

8. Key takeaways

  1. Session ID is the boundary. Everything private is scoped by chat_id. Two chats never share reverse-lookup tables.
  2. Tokens are deterministic hashes. Same value → same token, always. No random state, no drift.
  3. Full history is rewritten on every request. The proxy doesn't trust cached client-side pseudonyms — it re-runs Presidio + fallback re-scan on the whole payload.
  4. Redis stores the reverse map, not the tokens themselves. The tokens are derivable; the reverse map is what you need to restore the LLM's response.
  5. Confidential VM is the perimeter. Redis holds plaintext originals — safe because the whole VM is encrypted memory attested by Enclaive Nitride.
  6. Fallback re-scan is the safety net. Even if Presidio's NER model wobbles, the regex re-application of the session mapping keeps tokens consistent turn-to-turn.
