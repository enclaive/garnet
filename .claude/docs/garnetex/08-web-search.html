Web Search in Garnet

How normal prompts work vs. web-search-enabled prompts — with real timing data from production

01 — Two Ways a Prompt Can Flow

Normal prompt
1

User sends message

OWU receives the prompt. No web search active. Sends directly to proxy.

2

Proxy pseudonymizes

Presidio scans user message only. Fast — small input, no web content.

[IN USER] Max Mustermann → [OUT USER] PERSON_dddfab9b

3

LLM answers from training data

Only knowledge baked in at training cutoff. No live data. No citations.

4

Proxy depseudonymizes

Restores real names in LLM response before user sees it.

Web search prompt
1

User sends message (🔍 active)

OWU detects web search is enabled. Runs query expansion, calls DDGS.

2

DDGS fetches results ~16s

OWU searches Bing via DDGS, fetches page snippets, injects them as <source> blocks in the system prompt.

3

Proxy pseudonymizes everything

Scans user message + all web results. More content = more time.

[IN FILE] len=5264 → [FILE PII] 5 entities

[IN USER] Max → [OUT USER] PERSON_a1a5936d

4

LLM answers from training + live web

Sees pseudonymized web snippets as context. Cites sources. More accurate on recent topics.

5

Proxy depseudonymizes

Restores real names in response. Web result entities also restored.

02 — What is DDGS?

DDGS (DuckDuckGo Search)

A Python library that queries search engines without needing an API key. OWU uses it to search the web on the user's behalf.

  • No account or key required
  • Supports multiple backends: bing, google, yahoo…
  • Returns: title, URL, snippet per result

Backends matter

The duckduckgo HTML backend scrapes the DuckDuckGo website directly. DuckDuckGo blocks bots → returns 202 → OWU shows "An error occurred while searching".

Fix: switch to bing backend — stable, no bot detection issues.

Search query privacy gap

The search query sent to DDGS/Bing is NOT pseudonymized — it goes through OWU directly, bypassing the proxy.

Example: "Enclaive GmbH Berlin GDPR privacy policy" is sent to Bing unmasked.

The web results that come back are pseudonymized by the proxy ✅

03 — What Happens Inside OWU (Before Proxy Sees Anything)

1

Query expansion

OWU asks the LLM to rewrite the user's question into 2-3 better search queries. Example:

"GDPR data subject rights" · "Enclaive GmbH Berlin GDPR privacy policy" · "GDPR rights individual company Germany"

2

DDGS search

Each query runs against the selected backend (bing). Returns Result Count results per query — title, URL, snippet.

3

Web Loader (optional)

If Bypass Web Loader is OFF: OWU fetches the full HTML of each result page → strips to plain text → much more content but much slower (~10-20s extra).

If Bypass Web Loader is ON: skips page fetch, uses only the short snippet from DDGS (3-4 lines). Fast.

4

Embedding (optional)

If Bypass Embedding is OFF: OWU embeds the page content with nomic-embed-text on CPU, then does vector similarity search to pick the best chunks. This is the slowest step — 20-30s on CPU.

If Bypass Embedding is ON: skips embedding entirely, sends snippets directly. Recommended.

5

Inject as system prompt → send to proxy

OWU wraps the web results in <source id="1">...</source> tags and puts them in the system message. Now the proxy sees it as a file/RAG chunk.

[IN FILE] role=system len=5264

04 — How the Proxy Recognises Web Content

# main.py — source tag detection
is_file = (
    role == "system" and "<source" in original_content_text
)

# If <source> found → treat as file/RAG content → run file pseudonymization
if is_file:
    log_in_file(role, len(original_content_text), original_content_text)
    # ... scan for PII, pseudonymize, log [FILE PII]

Why <source> tag?

OWU wraps every web result in a <source id="N"> block so the LLM knows where each piece of info came from and can cite it. The proxy uses this same tag as a signal that the system message contains external content that needs pseudonymization.

What gets pseudonymized

  • All <source> content (web snippets or full pages)
  • User message
  • Conversation history (previous turns)

What does NOT get pseudonymized: the search query sent to DDGS.

07 — Recommended Admin Settings

Admin → Settings → Web Search

  • Engine: DDGS
  • DDGS Backend: bing ← not duckduckgo (bot blocked)
  • Result Count: 2
  • Bypass Embedding and Retrieval: ON
  • Bypass Web Loader: ON

Admin → Workspace → Models

  • Select your model → Capabilities
  • Web Search: ✅ enabled
  • Default Features → Web Search: ON

The 🔍 button in chat must be blue before sending.

Expected timing after settings

  • DDGS snippets: ~2s
  • Proxy pseudo: ~2s
  • LLM TTFT: ~4s
  • LLM generation: ~15-30s
  • Total: ~20-35s

Without web search: ~4-8s

08 — Privacy Status of Each Part

DataPseudonymized?Notes
User message ✅ Yes [IN USER] → [OUT USER]
Conversation history ✅ Yes [HISTORY PSEUDO] N message(s) — uses session MD5 cache
Web search results (injected context) ✅ Yes [IN FILE] → [FILE PII] → [OUT FILE] — treated as RAG chunk
Search query sent to DDGS/Bing ⚠️ No OWU sends it directly — bypasses proxy entirely. Real names leak to search engine.
LLM response ✅ Yes Depseudonymized before user sees it
