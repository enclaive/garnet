## TL;DR

- **"Stuck after 5 prompts" = 3 stacked bugs, not one.** Primary: `--workers 1` uvicorn + **sync Redis client used from async handler** (`mapping_store.py:9`) → every mapping read/write blocks the event loop; when Redis latency ticks up (or ollama slows), the whole proxy freezes. Secondary: unbounded global **`pseudo_cache: dict`** (`main.py:56`) never evicted. Tertiary: fresh `httpx.AsyncClient()` created per request (7 sites) — no keepalive, TCP+TLS handshake every LLM call, socket churn on the way to ephemeral-port exhaustion.
- **Ollama concurrency = 1 by default.** Compose sets no `OLLAMA_NUM_PARALLEL` / `OLLAMA_KEEP_ALIVE` / `OLLAMA_NUM_CTX`. Serial requests + 2048-token context = users hit truncation + hangs around turn 4-6 when history+RAG grows.
- **34 findings: 12 P0 (7 carryover, 5 new), 14 P1, 8 P2.** Biggest single fix by lines-of-code / user-impact ratio: **shared module-level `httpx.AsyncClient`** — ~20 lines of code, cuts p50 latency by 50-200ms per LLM call *and* fixes the socket-leak that surfaces as "stuck".
- **The previous audit's P0s were not merged.** `build_analyzer` still rebuilt per request, tokens still 32-bit, session_id fallback still MD5, MappingStore still leaks memory, Redis still plaintext. Re-surfacing under `[carryover]`.
- **Correctness bug I did NOT see previously:** the `pseudo_cache` at `main.py:56` is keyed by session_id → hash-of-text. Two users whose `session_id` collides via the MD5-fallback (P0-6 carryover) share `pseudo_cache` too. Compounding privacy leak.

## P0 — do these now

### 1. NEW — "Stuck after 5 prompts" root cause: sync Redis client in async event loop

- **Where:** `backend/privacy_proxy/app/mapping_store.py:7-15, 47-97` (all `_redis_client.get/setex/keys/ping` calls); called from async `proxy()` in `main.py`.
- **Why:** `redis.from_url(...)` returns a **synchronous** client. Every `_redis_client.get()` / `setex()` / `keys()` blocks the uvicorn event loop for the full Redis round-trip. With `--workers 1` (Dockerfile:23) and streaming SSE responses that keep the connection open for 30s+, one slow Redis query = every other in-flight request freezes. After 5 chats where any turn hits Redis latency (`KEYS` scan at main.py:630, 644 is O(all-keys)), the proxy visibly hangs. `KEYS` is also documented as "do not use in production" — it blocks Redis itself.
- **Fix (quick, ~15 lines, no protocol change):**
  ```py
  # mapping_store.py — swap sync client for async
  import redis.asyncio as aioredis

  _redis_client = None
  async def _init_redis():
      global _redis_client
      if REDIS_URL and _redis_client is None:
          _redis_client = aioredis.from_url(
              REDIS_URL,
              decode_responses=False,
              socket_timeout=2.0,
              socket_connect_timeout=2.0,
          )
          await _redis_client.ping()
      return _redis_client

  # Then make get/set/flush async: `await _redis_client.get(...)`
  # And in main.py replace `_redis_client.keys("garnet:mapping:file:*")` with SCAN:
  cursor = 0
  keys = []
  while True:
      cursor, batch = await _redis_client.scan(cursor, match=b"garnet:mapping:file:*", count=200)
      keys.extend(batch)
      if cursor == 0:
          break
  ```
- **Effort:** M (touches mapping_store + 4 call sites in main.py). But no data-migration — same Redis keys.
- **Priority:** P0
- **Expected gain:** eliminates the head-of-line block. p99 latency drops from "unbounded / hang" to Redis-round-trip (~2ms). Removes the primary root cause of the "stuck after 5" symptom.

### 2. NEW — Unbounded global `pseudo_cache` at main.py:56 (memory leak / correctness)

- **Where:** `backend/privacy_proxy/app/main.py:56, 85-95`
- **Why:** `pseudo_cache: dict[str, dict[str, str]] = {}` — global, per-session-id nested dict of `md5(text) → pseudonymized_text`. **Never evicted.** Every user message adds an entry per unique history string; over a long-lived pod, this grows without bound (worse than MappingStore because it hashes *every* history message, not just PII sessions). At `--workers 1` this alone eats the proxy's memory allotment (10G in compose, less on k8s) after enough traffic. And — combined with P0-6 carryover — if two users share the MD5-fallback session_id, they share their pseudo_cache slice too: **cross-user privacy leak**.
- **Fix:**
  ```py
  # main.py — replace the global dict + helper with a bounded LRU
  from functools import lru_cache
  from cachetools import TTLCache   # cachetools is already transitively installed via presidio? verify
  # or stdlib-only: OrderedDict-based bounded cache.
  # Simplest ponytail path: piggyback on MappingStore's TTL sweep by moving pseudo_cache INTO the session's mapping struct.
  # But smallest independent fix:
  from collections import OrderedDict
  _PSEUDO_CACHE_MAX = 5000  # entries across all sessions
  pseudo_cache: "OrderedDict[tuple[str, str], str]" = OrderedDict()

  def _pseudo_with_cache(text, session_id, enabled_types):
      if not text:
          return text
      key = (session_id, hashlib.md5(text.encode("utf-8")).hexdigest())
      hit = pseudo_cache.get(key)
      if hit is not None:
          pseudo_cache.move_to_end(key)
          return hit
      out = pseudonymize(text, session_id, store.get_store(), enabled_types=enabled_types)
      pseudo_cache[key] = out
      if len(pseudo_cache) > _PSEUDO_CACHE_MAX:
          pseudo_cache.popitem(last=False)
      return out
  ```
- **Effort:** S
- **Priority:** P0
- **Expected gain:** bounded RSS. Proxy no longer OOM-kills on k8s under long uptime. Removes cross-user cache leak.

### 3. NEW — Fresh `httpx.AsyncClient()` per request (7 sites) — TCP+TLS churn + socket leak

- **Where:** `main.py:149, 368, 723, 759, 789, 866`. Every LLM call opens a new client.
- **Why:** `async with httpx.AsyncClient() as client:` inside the request handler means: TCP handshake + TLS negotiation on every OpenAI/Anthropic/Ollama call. p50 adds ~50-200ms per call. On the streaming path, the client context manager exits *while the generator is still yielding* to StreamingResponse → the inner `async for chunk in resp.aiter_bytes()` runs against a closing client → connections held in TIME_WAIT, occasionally leaked. Under sustained load this can exhaust ephemeral ports (Linux default ~28k).
- **Fix (module-level shared client with lifespan):**
  ```py
  # main.py — top-level
  from contextlib import asynccontextmanager

  http_client: httpx.AsyncClient | None = None

  @asynccontextmanager
  async def lifespan(app):
      global http_client
      limits = httpx.Limits(max_connections=100, max_keepalive_connections=50, keepalive_expiry=30.0)
      http_client = httpx.AsyncClient(timeout=httpx.Timeout(120.0, connect=5.0), limits=limits)
      yield
      await http_client.aclose()

  app = FastAPI(default_response_class=ORJSONResponse, lifespan=lifespan)

  # Then replace every `async with httpx.AsyncClient() as client:` with `client = http_client`
  # For the streaming case: use `http_client.stream(...)` — it returns an async context manager on the response, not the client.
  ```
- **Effort:** M
- **Priority:** P0
- **Expected gain:** p50 LLM latency −50-200ms. Eliminates socket churn. Streaming path becomes correct — no more "client closed while generator still yielding".

### 4. NEW — Uvicorn `--workers 1` + no async concurrency guard

- **Where:** `backend/privacy_proxy/Dockerfile:23`
- **Why:** Single worker is fine for async IO, but Garnet's request handler does synchronous CPU work inside the async path — spaCy `analyzer.analyze()` (pseudonymizer.py:166), GLiNER `predict_entities()` (pseudonymizer.py:132), regex passes, hashlib. All of these are sync and hold the event loop. Combined with sync Redis (P0-1), a single slow message stops every other in-flight request. That's the "5 prompts" symptom in a nutshell.
- **Fix (two-part, both small):**
  1. Wrap CPU-bound calls in `asyncio.to_thread(...)` — smallest change with the biggest win:
     ```py
     # pseudonymizer.py — in detect_entities, wrap the heavy calls
     import asyncio
     # Actually — detect_entities is sync. Wrap at call site in main.py:
     out = await asyncio.to_thread(pseudonymize, text, session_id, store.get_store(), enabled_types=enabled_types)
     ```
     This releases the event loop while the C-level spaCy work runs.
  2. Bump workers to 2 (or use `--workers ${WEB_CONCURRENCY:-2}`) — every worker is a separate spaCy+GLiNER copy (~2-3 GB each), so keep to 2 within the 10G limit.
- **Effort:** S (thread offload) + S (Dockerfile CMD)
- **Priority:** P0
- **Expected gain:** other requests remain responsive during a long chat. "Stuck after 5" symptom disappears even without fixing P0-1 (though ideally do both).

### 5. NEW — Ollama defaults: `num_parallel=1`, `num_ctx=2048`, no keep-alive — the real "5 prompts" limit

- **Where:** `backend/privacy_proxy/docker-compose.yml:17-32`, proxy sends no explicit `options.num_ctx`.
- **Why:** Ollama defaults to `OLLAMA_NUM_PARALLEL=1` (serial) and `num_ctx=2048` unless the model's Modelfile overrides. After 4-5 turns with RAG chunks (`top_k=15`, hybrid on) + history, the context blows past 2048 → truncation + occasional silent hangs. And `OLLAMA_KEEP_ALIVE=5m` default means the model unloads between chats, adding cold-start latency.
- **Fix (compose env):**
  ```yaml
  ollama:
    environment:
      - OLLAMA_NUM_PARALLEL=2
      - OLLAMA_KEEP_ALIVE=30m
      - OLLAMA_MAX_LOADED_MODELS=2
  ```
  And in the proxy for Ollama chat body:
  ```py
  # main.py — inside is_chat branch when provider_label == "ollama"
  body.setdefault("options", {})
  body["options"].setdefault("num_ctx", 8192)
  ```
- **Effort:** S
- **Priority:** P0
- **Expected gain:** context fits ~5x more history. Model stays warm between turns. Serial → 2-way concurrency. Directly addresses the "gets stuck around 5 prompts" story.

## P1 — worth a sprint

### 13. Sync spaCy/GLiNER calls not offloaded from async loop

- **Where:** `main.py:604, 662, 703` — direct `pseudonymize(...)` calls inside async handler.
- **Why:** Even with P0-4's thread offload for the last-message call, history-loop still calls sync `_pseudo_with_cache` in a tight `for` (main.py:517-533). On a long conversation this is hundreds of ms of loop-blocking per turn.
- **Fix:** Move the history loop into a single `asyncio.to_thread(...)` batch. Or, parallelize across messages with `asyncio.gather(*(to_thread(...) for msg in messages[:-1]))`. spaCy is thread-safe on read; the analyzer is shared.
- **Effort:** S

### 14. Query Expansion runs sequentially before main LLM (~7s added)

- **Where:** `main.py:687` — `variants = await expand_query(...)` before spawning the streaming response.
- **Why:** User waits for gpt-4o-mini to return before their real answer starts streaming. Ahmed already flagged this in `tasks.md`.
- **Fix:** Kick expand_query off with `asyncio.create_task(...)`, race it against a small timeout (~1.5s), inject variants if they arrived, drop them otherwise. Or run expand + main in parallel and merge variants into RAG lookup separately.
- **Effort:** M

### 15. `hist_pseudo_count` scan re-detects PII on every turn

- **Where:** `main.py:517-533` — walks `messages[:-1]` and re-pseudonymizes each history message.
- **Why:** OWU already sent the previously-pseudonymized text in history (visible from the `has_pseudo` tag check at 522). Re-running detect_entities on already-pseudonymized text is redundant work; only actually needed for messages the client sent raw. The current heuristic (SYSTEM_PROMPT_MARKERS skip) misses this.
- **Fix:** skip messages where `has_pseudo` is true — trust the client's history. Costs one line:
  ```py
  if has_pseudo:
      continue
  ```
- **Effort:** S

### 16. `session_mapping` scan for `file:*` on every request

- **Where:** `main.py:737-739, 781-783`
- **Why:** Iterates every in-memory session on every chat message. As sessions accumulate (P0-8 carryover unfixed), this is O(n_sessions) per request.
- **Fix:** maintain a `file_session_index: set[str]` on MappingStore, updated on file scan / eviction. Iterate only that set.
- **Effort:** S

### 17. `stream_with_depseudo` inefficiency inside chunk loop

- **Where:** `main.py:257, 271` — `sorted(mapping.keys(), key=len, reverse=True)` and full `.replace()` per chunk.
- **Why:** For a 500-chunk stream with 30 tokens, that's 15k `.replace()` calls plus 500 sort() calls. Also the sort is `sorted` (allocating) not `sort` on a pre-built list.
- **Fix:** compute `sorted_tokens = sorted(mapping.keys(), key=len, reverse=True)` once above the async for. Bigger win: precompile a single regex `re.compile("|".join(map(re.escape, sorted_tokens)))` and use one `.sub(callback)` per chunk. ~5x faster on typical mapping sizes.
- **Effort:** S
